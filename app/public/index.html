One Oracle schema, two ways to Postgres: orafce + ora2pg on community PostgreSQL, or EPAS. Both run live, side by side.

Moving off Oracle: orafce + ora2pg, or EPAS?

Two routes lead from Oracle to Postgres. Route A stays on community PostgreSQL: ora2pg converts the schema and the code, the orafce extension supplies Oracle-style functions, and people fix what is left. Route B moves to EDB Postgres Advanced Server (EPAS), a Postgres that understands Oracle's SQL, PL/SQL, packages and data semantics itself, so most code is moved rather than converted. This lab runs both routes against the same live Oracle database, so you can compare the outcomes instead of the brochures.

Route A

Community PostgreSQL 18 + orafce + ora2pg

orafce is an open-source extension that adds Oracle-compatible functions (NVL, DECODE, ADD_MONTHS …), the varchar2 type, DUAL, and libraries such as DBMS_OUTPUT, DBMS_PIPE and UTL_FILE. It does not touch the SQL parser, so Oracle-only syntax still fails.

ora2pg is an open-source Perl tool that assesses an Oracle schema, converts DDL and PL/SQL to PostgreSQL syntax, and copies the data.

Route B

EDB Postgres Advanced Server 18, Oracle-compatible mode

EPAS is PostgreSQL plus EDB's Oracle compatibility built into the server: SPL and PL/SQL, packages, ROWNUM, CONNECT BY, (+) joins, MINUS, synonyms, NUMBER / VARCHAR2 / DATE types, autonomous transactions, and a long list of DBMS_* / UTL_* packages.

EDB Migration Toolkit copies schema and data straight from Oracle. Or you simply run your existing Oracle scripts against it and see what complains.

The test subject: ACME live from Oracle

A small order-management schema, written to be full of the Oracle idioms real systems accumulate: a PL/SQL package with state, constants, BULK COLLECT and an autonomous transaction; triggers; hierarchical queries; ROWNUM; old-style outer joins; sequences; a synonym.

How to run this demo about 20 minutes

  1. Assess: read the Oracle source, see which parts are Oracle-specific, and run ora2pg's own assessment.
  2. Migrate: run Route A and watch what breaks, apply the manual fixes, then run Route B with the same Oracle database as the source.
  3. Same SQL, three engines: fire the same Oracle statements at Oracle, PostgreSQL + orafce and EPAS and read the verdicts.
  4. Scorecard and Considerations: what the lab measured, and when to pick which route.
The SQL Console (top right) runs SQL against all three databases. Reset lab drops both migrated schemas so you can start again.

How this lab is wired

Four containers: Oracle Database Free holds the source (loaded from oracle/sql/*.sql); PostgreSQL 18 + orafce is Route A's target; EPAS 18 initialised with --redwood-like (Oracle-compatible mode) is Route B's target; and this web app, which also carries the real tools it drives: ora2pg 25, EDB Migration Toolkit and psql. Nothing is mocked: every console on the Migrate tab streams the actual output of those tools, and every verdict on the test bench is a real query on a real engine.

What this lab does not tell you. The ACME schema has about 50 objects and 9,000 rows. Use it to understand the kinds of problems each route has, not to predict the size of your project. Performance, high availability, licensing cost and your own application code are outside its scope; assess your real schema with ora2pg's report and with EDB's Migration Portal.
